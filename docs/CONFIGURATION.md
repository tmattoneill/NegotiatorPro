# Configuration system

NegotiatorPro uses a dual-configuration approach to separate static, version-controlled settings
from dynamic runtime state.

## `config.json` — centralised settings

- **Purpose**: app-wide settings, UI configuration, and system defaults.
- **Location**: `/config.json`.
- **Access**: via the `/api/config/*` REST endpoints.
- **Management**: manually edited, version-controlled.

Contains app metadata (name, version, environment), UI theme colours and feature flags, system
limits (max message length, session timeout), security settings (JWT expiration, password
requirements), and PLEASE framework configuration. It does **not** contain LLM model definitions —
those live in `backend/llm_backend_config.py`.

Key endpoints:

```bash
GET  /api/config/          # Full configuration
GET  /api/config/app       # App info only
GET  /api/config/ui        # UI settings
GET  /api/config/defaults  # Default settings
POST /api/config/reload    # Reload config.json without restart
```

Usage:

```python
from backend.config_loader import config

app_name = config.get("app.name")
max_length = config.get("ui.limits.maxMessageLength")
enable_profiles = config.get("ui.features.enableUserProfiles")
```

## `llm_backend_config.json` — runtime LLM state

- **Purpose**: track active LLM backend selections and runtime state.
- **Location**: `/llm_backend_config.json`.
- **Access**: via the `LLMBackendManager` class.
- **Management**: auto-generated by the backend, modified through the admin interface, gitignored.

```json
{
  "active_backend": "openai",
  "active_models": {
    "default": { "backend": "openai", "model": "gpt-4o-mini" },
    "premium": { "backend": "anthropic", "model": "claude-3-5-sonnet-20241022" }
  },
  "backend_settings": {
    "openai": { "enabled": true },
    "anthropic": { "enabled": true },
    "ollama": { "enabled": false }
  }
}
```

LLM model definitions (`ModelInfo` objects with pricing, capabilities, context length) are
hardcoded in `backend/llm_backend_config.py` as the `BACKENDS` dictionary. This keeps the RAG engine
and admin interface consistent.

### Adding a new model

1. Edit `backend/llm_backend_config.py`.
2. Add a `ModelInfo` entry to the relevant backend's `models` list (id, name, description, pricing,
   context length, capabilities).
3. Restart the backend — the model is immediately available in the admin interface.
4. Do **not** edit `config.json` for models (the deprecated section is marked
   `llm_models_DEPRECATED`).

## Why the split

Static configuration (`config.json`) covers UI behaviour, feature flags, and security settings — it
rarely changes and is version-controlled. Dynamic runtime state (`llm_backend_config.json`) covers
current model selections and backend availability — it changes frequently via the admin interface
and is not version-controlled.

## Database vs JSON files

- **PostgreSQL**: user accounts and authentication, user profiles and preferences, encrypted user
  API keys, conversation history, partner personas, the source registry, session tokens.
- **JSON files**: system-wide settings (`config.json`), LLM backend state
  (`llm_backend_config.json`), admin sessions (`admin_sessions.json`), usage statistics
  (`usage_stats.json`), prompt templates (`prompt_config.json`).

User-specific data needs relational integrity and scale (PostgreSQL); system configuration benefits
from simple file-based management with version control.
